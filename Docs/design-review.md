## 一、架构级风险（开工前必须定案）

### R1. 跨轮次 Job 持有的 BehaviorInfo 引用 vs 冷卸载竞态（悬空引用）

- **优先级**：P0
- **涉及章节**：3.3、6.1、7.2、11（EvictColdData）
- **问题**：Job 挂起在 `WaitForRpc`/`WaitForLoad` 时已持有 `info` 引用（如 6.1 示例 `info.gold -= cost` 之前的 `yield return _store.Get(...)`）。挂起期间主循环可能把该 BehaviorInfo 冷卸载。
- **缺陷本质**：7.2 声称"不需要引用计数"，但**跨轮次 Job 里的局部引用就是隐式引用**。卸载后 Job 恢复，`info` 指向已从内存移除的对象，行为未定义。
- **建议方向**：二选一，必须定一个：
  1. 卸载前检查"是否有挂起 Job 涉及该 BehaviorInfo"（维护最小活跃集合）；
  2. 规定 Job 恢复时必须重新 `Get`，禁止跨 yield 持有引用（Analyzer 强制）。②更符合单线程哲学，但需改 6.1 示例写法。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 结论：采纳建议方向①——**Job 级引用计数**。Job 通过 `DataStore.Get` 获得引用时计数 +1，Job 结束（Commit/Rollback/异常/取消）统一释放；计数 > 0 的 BehaviorInfo 在 Evict 时跳过，即使超时间阈值也不卸载。挂起 Job 跨调度轮次的引用因此受保护。
  - [2026-08-02] 可行性依据（用户明确）：单线程协作式下卸载只发生在主循环 `EvictColdData` 边界（所有 Job 均在 yield 挂起点），引用计数生命周期与 Job 生命周期一一对应，无需全局引用追踪。
  - [2026-08-02] 已回写 architecture.md：3.2 加引用计数保护段；7.2 判定改为"时间跨度 + Job 引用计数"双条件；3.1 加"每个 Actor 同一时刻只执行一个 Job，调度切换只发生在不同 Actor 的 Job 之间（所有 Service 同语义）"；11 章 EvictColdData 注释、12.1 验证项（挂起 Job 引用不被卸载）、决策表 #4 同步。

### R2. at-least-once 的"发送端保证"缺失（outbox）

- **优先级**：P0
- **涉及章节**：9.3、10
- **问题**：9.3/10 定义了消费端幂等（eventId、去重记录、死信），但**发送端 outbox 是否持久化、谁来重发、崩溃后未发送的事件怎么办——没写**。10 章只提"热迁移前 flush 已提交但未发送的跨服务事件"。
- **缺陷本质**：outbox 只在内存时，进程崩溃 = 已 Commit 未投递的事件**直接丢**——at-least-once 实际退化成 at-most-once，账目类级联（交易通知、补偿触发）会漏。
- **建议方向**：明确 outbox 落库（与事件同一 DB 或专用集合）+ 投递确认后删除 + 定期重扫重发。这是"at-least-once"成立的前提，不是可选项。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 结论：**outbox 不引入**。定案为**数据所有权原则**——谁的数据放谁身上：状态真相归属某个 Actor 的 BehaviorInfo，存在其所属 Service；多方原子变更必须落在同一 Service 用 must 完成；跨 Service 只传通知/曝光，不承载真相，丢失通过重新曝光/查询恢复，at-most-once 可接受。跨 Service 不存在状态转移 → outbox 失去存在意义。
  - [2026-08-02] 解题过程（用户例子）：拍卖场景——上架 auctioninfo 记在卖家 A 身上（真相在 A）、出价/冻结押金记在买家 B 身上（真相在 B）、成交 = A/B 两个 player 的 must（同 Service 批原子）、auction.service 只做曝光不持真相 → 全程无跨 Service 状态转移，事件全是通知。
  - [2026-08-02] 判定边界：可对账事件（接收方有可查记录 + 有对账触发点 + 玩家会主动发现）→ 业务手段兜底，无需 outbox；不可对账场景（触发源在发送方、接收方无对账键）→ 属设计错误，回上层改数据归属，而非加补偿机制。
  - [2026-08-02] 附带产出：**跨服务业务解题 SOP**（10.3）——列实体 / 判原子 / 归位 / 降级 / 验证五步，适用于交易、竞拍、组队结算等"两个实体之间发生业务"的场景。
  - [2026-08-02] 可行性前提补充（用户）：**虚拟化 Actor 离线读写**——对方不在线时 must 也能按离线路径（SeekDeep 激活 + BehaviorInfo 落库）捞取参与方数据完成交易，真相留在参与方身上不因离线而不可用，第三方无需兜底、无需等待上线（已并入 10.1 可行性基础段 + 10.3 第 2 步）。
  - [2026-08-02] 已回写 architecture.md：10.1 数据所有权原则 + 10.2 通知语义（跨服务事件改尽力投递）+ 10.3 SOP；9.2 加数据所有权约束；12.1 验证项（跨服务通知丢失可恢复）；决策表 #24/#25。

### R3. 投影路径未闭环（Service → 客户端怎么走）

- **优先级**：P1
- **涉及章节**：2（拓扑）、4.2（gatewayAddr）、8.2
- **问题**：拓扑图客户端只连 Gateway，但 8.2 只说"Transport 发送 ProjectorPacket"——**Service 的投影是直连客户端还是经 Gateway？经哪个 Gateway 实例？** 没写。
- **缺陷本质**：投影必须回到持有该客户端 session 的那个 Gateway 实例——需要 `online:{actorId} → gatewayAddr` 的路由参与（4.2 有 gatewayAddr，但投影侧机制没写）。
- **建议方向**：在 8.2 明确"投影 = Service → 目标 Gateway（按 gatewayAddr）→ 该 Gateway 上 session 直发"，并把"Gateway 实例连接映射表"纳入 Router 数据面。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 用户裁决：**R3 本质是"通过路由找回玩家的 Gateway"**——4.2 路由数据面 `online:{actorId} → {serviceAddr, gatewayAddr}` 已含 gatewayAddr，只是 8.2 未写明投影侧机制，属**文档断点而非机制缺口**。
  - [2026-08-02] 结论：投影寻址复用 4.2 既有路由，不新增机制——Service 投影时查 Router 取 `online:{actorId}.gatewayAddr`，将 `ProjectorPacket` 发往该 Gateway，由 Gateway 用本地 session 直发客户端。无需新增"Gateway 连接映射表"：`gatewayAddr` 本身就是 session 归属映射，映射实体由 Gateway 自持。离线 Actor 无 `online` 路由 → 投影挂起/丢弃，重连时请求全量快照（5.1）。
  - [2026-08-02] 已回写 architecture.md：8.2 加"投影目标寻址"段；12.1 加投影路由验证项；决策表 #26。

### R4. 容量模型缺失（运营无法规划，且调度可能 O(N) 每轮）

- **优先级**：P1
- **涉及章节**：3.3（调度预算）、4.1（Cold 壳常驻）、12.3（可行性表）、13（路线）
- **问题**：全文没有量化目标——单实例单线程每秒 Job 吞吐、单实例 CCU、内存上限、扩容水位全无数字；12.3"高 CCU 容量"只标"中"。
- **缺陷本质**：3.3 按 Actor 的 starvationFrames 算预算，暗示每轮遍历全部 Actor；百万级壳常驻（4.1 Cold 壳不参与冷热）时，**每轮全扫 = O(所有 Actor)**，在线 30 万 + 壳百万，纯扫描开销压垮单线程。
- **建议方向**：调度器必须引入"就绪集合"（只有可推进的 Job/Actor 进 ready set），Evict/扫描按分桶懒化；并在 13 章给压测目标数字（如单实例 ≥5k Job/s、≥3 万在线、P99 RPC ≤50ms）。
- **状态**：☑ 已解决（定位已定案；量化数字待 Phase 5 压测实测校准）
- **解决记录**：
  - [2026-08-02] 用户裁决：**容量数字必须以实际性能为约束，不拍脑袋**。ready set（就绪集合）作为**结构性要求先行**——调度器第一版即实现，避免每轮遍历全部 Actor 的 O(N) 全扫；量化目标（单实例 Job/s、CCU、P99）以 Phase 5 压测实测为准，写入时用实测校准值。因此 R4 不属于"开工前必须定案"，随 Phase 2（调度器实现）+ Phase 5（压测）落地。已回写决策表 #27。
  - [2026-08-02] 状态标记更新：定位部分（ready set 结构性先行）已定案，补入 3.3 正文与决策表 #27；仅剩"量化数字"属 Phase 5 压测产出，不是未决设计问题。

## 二、实现级缺口（Phase 1-2 就要明确的细节）

### R5. RPC 入口的 actorId 来源（越权风险）

- **优先级**：P0
- **涉及章节**：6.1
- **问题**：6.1 示例 `Spend(ulong actorId, int cost)` 把 actorId 当参数——若客户端可传，就是任意越权（A 花 B 的钱）。
- **缺陷本质**：目标身份来自不可信输入。
- **建议方向**：规定 `[RpcMethod]` 的 actorId **由框架从 session/认证上下文注入**，签名里不允许客户端指定目标。示例要改写法。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 用户裁决："使用你的建议，它可以指定对哪个玩家。但是自己就是自己，这是鉴权"——**主体身份注入 = 鉴权；目标 = 业务参数**。
  - [2026-08-02] 结论：`[RpcMethod]` 执行主体（actorId）由框架从 session/认证上下文注入，**调用者恒为自己**，客户端无法以他人身份发起（防 A 花 B 的钱）；"指定对哪个玩家"的需求不消失，作为**业务参数**（如 `targetActorId`）传入，由服务端业务代码做关系/权限/黑名单校验，框架不做业务拦截。Service→Service 的 `Call`/`Fetch` 目标由服务端代码指定，属受信上下文，经 Router 寻址，不涉客户端越权。
  - [2026-08-02] 已回写 architecture.md：6.1 示例改 `Spend(int cost)` + `CallContext.actorId` 注入 + 新增 `SendGift(targetActorId, ...)` 业务目标示例 + 规则条目；9.3 补"RPC 主体鉴权"段；12.1 加验证项；决策表 #28。

### R6. Redis 依赖的三处空洞

- **优先级**：P1
- **涉及章节**：5.2、4.2、4.3
- **问题**：
  1. `online:{actorId}` TTL 5s：**谁续期、频率多少**没写——漏续期 = 在线玩家被误判离线、消息路由到错实例。
  2. Redis 故障降级：5.2 只一句"短期缓存降级"，Router 完全靠 Redis 时，Redis 挂 = 全系统不可寻址。
  3. 迁移期间（4.3 可能 >5s）online key 过期窗口：迁移要保活续期。
- **建议方向**：① 明确心跳续期归属与频率；② Router 多级缓存（内存 + Redis + 可配置兜底）；③ 迁移期间保活续期。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 结论（三处分别定案）：
    1. **续期归属**：`online:{actorId}` 由 **Actor 宿主的 Service** 续期——Actor 处于内存活跃态（Hot 或缓冲期）即续期，频率 ≤ TTL/2（默认 2s），Actor 管理循环批量续期合并 Redis 往返；看门狗（3.1）是进程级 liveness，与 Actor 级 online 续期解耦；**Gateway 不续期**（连接与 Actor 活跃解耦，缓冲期内 Actor 仍在内存必须保持路由）。
    2. **Redis 降级**：Router 读路径全走**内存镜像**（online/players/hashring 常驻），Redis 只做真相源；故障时按**陈旧窗口**（默认 60s）继续读；写失败进**待同步队列**，恢复后回放；超窗口未恢复 → 拒绝新寻址或回退一致性哈希 fallback（离线 Actor 定位 home 不依赖 online）。Redis 故障只影响"新变更可见"，不影响既有寻址。
    3. **迁移保活**：进入 `Prepare` 时对 `online:{actorId}` 显式保活（TTL 覆盖迁移窗口，如 30s），归属发布后新实例接管续期，旧实例 `Redirect` 前不撤销。
  - [2026-08-02] 已回写 architecture.md：4.2 加"在线状态续期"段；5.2 加"Redis 故障降级"段；4.3 迁移约束加保活续期；12.1 加验证项；决策表 #29。

### R7. lastAccessAt 语义未定（冷热判定无法实现）

- **优先级**：P1
- **涉及章节**：7.2
- **问题**：按 lastAccessAt 时间跨度判定冷热，但**谁更新？读算访问还是写算？存内存还是 DB？** 若读即更新 → 热读数据永不卸载且每次读都脏写；若只写更新 → 语义符合"最后使用"。若字段存 DB，会引入写放大。
- **建议方向**：只在**写提交时**更新 lastAccessAt，且放内存（不落 DB），卸载/重启后以上次 Truck 落库时间为准（接受冷启动偏差）。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 用户裁决：**读写都算访问**（不限于写提交），并纠正误解——**在线不等于数据被保鲜**：数据只被 Job 触碰，玩家挂机时无 Job Get 该 BehaviorInfo，时间戳照样老化、照样卸载；"读"不是在线持续读，而是 Job 按需懒加载的读。
  - [2026-08-02] 结论：`lastAccessAt` 由 **Job 通过 DataStore.Get 的读写**刷新（读=Get 加载时、写=提交时），读和写都算访问；字段**只维护在内存、不落 DB**——读刷新不产生脏写（规避读放大），卸载时随之丢弃，重新加载从加载时刻重新计时；重启接受冷启动偏差，仅影响首轮卸载时机，不影响业务正确性。
  - [2026-08-02] 已回写 architecture.md：7.2 加"lastAccessAt 语义"段；12.1 加验证项；决策表 #30。

### R8. baseVersion 一致性视图未定义

- **优先级**：P1
- **涉及章节**：8.2
- **问题**：8.2 有 baseVersion 兜底，但**一个 Actor 多个 BehaviorInfo 各推各的 diff，客户端如何对齐成一致快照**？背包和钱包的投影来自不同轮次，客户端可能看到"钱包扣了、背包没加"的中间帧。
- **建议方向**：同一 Actor 的投影按统一版本/批次标签（一次 Job 提交 = 一个版本），客户端按版本整体应用，缺号才请求全量。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 用户裁决：**"那肯定不行啊。一个 job 多少会包含多个 info 的。你这个问题更像是，整包的问题，还有顺序问题"**——多 BehaviorInfo 独立推 diff 不可接受（Job 常态改多个 info），"客户端按版本聚合"是绕弯方案；本质是**打包 + 顺序**问题。
  - [2026-08-02] 结论：**一次 Job 提交 = 一个投影整包**，包内含该提交改动的所有 BehaviorInfo 的 diff（钱包+背包同包）；客户端以包为原子接收单元**整体应用，绝不部分应用**，机制上杜绝中间帧；包间按提交顺序发送、客户端按序应用（可靠通道保证）；缺包（commitId 不连续）→ 请求全量。**不再需要每个 BehaviorInfo 独立投影版本**，baseVersion 收敛为包级 commitId 连续性校验，更简单。
  - [2026-08-02] 已回写 architecture.md：8.2 投影协议段改写为"投影打包与顺序"（commitId + 包内 diff 列表 + 整体应用 + 缺号全量）；决策表 #31。
  - [2026-08-02] 用户补充：**投影只负责状态正确性，还会尾随一个事件通知 RPC**——"保证 property 同步完成之后，rpc 紧随。客户端通过这个来做时机表达"。投影 diff 不表达业务语义（金币变化看不出是交易成功还是系统补发），事件 RPC 显式承载语义，客户端先应用状态、收到事件后再触发表现。
  - [2026-08-02] 结论补充：投影整包之后**尾随事件通知 RPC**，同一可靠通道先投影后事件按序发送；事件 RPC 只带事件语义（类型 + 引用参数）**不承载状态真相**，丢失仅损失表现时机、不影响状态正确性；重连全量快照兜底后不重放事件。
  - [2026-08-02] 已回写 architecture.md：8.2 加"投影与事件通知 RPC"段；12.1 加验证项；决策表 #32。

### R9. must 的加载失败路径未定义

- **优先级**：P1
- **涉及章节**：9.2
- **问题**：离线参与方在临界区外预加载——**加载超时/失败呢？** must 取消并返回错误码？还是延迟再试？
- **缺陷本质**：不明确则参与方多时 must 的确定性失效。
- **建议方向**：定义失败语义（取消 + 错误码 / 延迟重试），保证 must 要么全成要么全败且可判定。
- **状态**：☑ 已解决
- **解决记录**：
  - [2026-08-02] 用户裁决：**"使用你的建议，must 可以自己定义重试次数，超时，must 只有全成，全败！"**
  - [2026-08-02] 结论：must 类可自定义**重试次数与超时**（框架给默认值、发起方可覆盖）；参与方预加载失败（超时/IO 错误/不可达）时按 must 定义的重试策略在**临界区外**重试，重试耗尽或超时 → **must 整体失败（全败）**，零副作用返回失败原因码，发起方按错误码决定重试或放弃。**must 只有全成或全败两种结果，不存在部分成功**：加载阶段重试只是延迟进入临界区，不改变"要么一次跑完所有参与方、要么零副作用回滚"的原子语义。

### R14. 崩溃一致性窗口：客户端已确认成功 vs MongoDB 未落库

- **优先级**：P0

- **问题**：玩家离线后，多个 Service **同时** `SeekDeep`（A 的好友邮件、B 的交易请求）→ 一致性哈希定位 home 实例，但**两个调用方可能同时激活、甚至不同实例各自加载同一 actorId 的 BehaviorInfo 并发写**——唯一归属不变量（1.3）在离线激活路径上**没有锁/仲裁**。
- **缺陷本质**：在线路径有 session/online 路由约束，离线激活路径**只有"定位"、没有"独占"**；哈希环定位 home 与"在线时宿主实例"可能不同，激活即隐含迁移，4.3 迁移状态机没覆盖"多个发起方撞同一个离线激活"。
- **建议方向**：离线激活必须**先取激活权**——Redis 原子操作（`SET nx` 激活锁 / 或直接走 4.3 迁移流程拿到归属）后**由获权实例独占加载执行**，其余调用方等结果或拿 `Redirect`；把"SeekDeep 激活"明确并入"排他归属获取"。
- **状态**：☒ 不成立（用户否决，2026-08-02）
- **否决理由**：离线激活的 home 由一致性哈希**确定性**定位——同一 actorId 在同一哈希环视图下恒指向唯一 home Service，激活只在该 home 发生一次；并发 `SeekDeep`（A 好友邮件、B 交易请求）按同一哈希收敛到同一 home，由 home 单线程调度 + 激活幂等（已激活复用 / 激活中等待）消化，**不需要 Redis 激活锁**。唯一破坏确定性的场景（哈希环视图不一致 / 节点增减）由既有 4.3 迁移状态机覆盖——版本条件写 + Router 版本化归属 + `Redirect`、新旧实例不可同时可写——"激活"与"迁移"本就共用同一条排他归属防线，不新增机制。已回写 architecture.md 4.2 加"离线激活即排他归属获取"澄清段；R16 从开工前清单移除。

### 二、实现级缺口（Phase 1-2 明确）

### R17. must 的提交/投影边界未定义

- **优先级**：P1
- **涉及章节**：9.1、9.2、8.2
- **问题**：投影边界 = "Job 提交边界"（9.1），但 must 是**临界区、不是 Job**。must 改了 N 个 Actor 的字段，**何时收集投影？按 Actor 各自打包？事件何时尾随？** 文档 9.2 全程没提 must 的投影与事件时序。
- **缺陷本质**：R8 解决了"一个 Job 多 BehaviorInfo 同包"，但 must 是"一次临界区多 Actor 多 BehaviorInfo"——**没有对应的打包语义**。若各自 Actor 独立收集，原子性只存在于服务端内存态；交易场景需要明确的投影+事件时序（否则 A 看到扣款、B 迟迟没看到到账）。
- **建议方向**：明确 must 完成 = 一次提交事件：受影响 Actor 各自投影（**must 类可声明参与方投影语义**），并在全部参与方投影后按序尾随"交易完成"事件 RPC；must 返回值带上"已完成投影"保证。
- **状态**：☑ 定案（2026-08-02，用户定案：must 完成后内部发送 RPC 事件）
- **定案记录**：must 全部成功 = **一次原子提交**——框架在 must 内部完成投影与事件发送，发起方与参与方业务**零代码**：①各参与方字段变更按各 Actor **各自投影整包**下发（各自 `commitId` 推进、各自整体应用，复用 8.2 打包语义），收集发生在 must 完成后同一调度轮次边界；②全部参与方投影后，must **内部**按序尾随"完成事件"RPC（复用 8.2"投影整包后尾随事件通知"机制：同通道先投影后事件，事件语义由 must 类声明、只带引用不承载真相、丢失仅损表现）；③全败路径不投影、不事件、零副作用（R9/9.2）；④发起方读 must 返回值即获"已完成投影与事件"保证。已回写 architecture.md 9.2 加"must 完成 = 一次原子提交"段、12.1 加验证项、决策表 #45。

### R18. commitId 的重启语义（全量风暴隐患）

- **优先级**：P1
- **涉及章节**：8.2
- **问题**：commitId 单调递增、客户端校验连续性。**进程重启后 commitId 从哪继续？** 若归零——所有活跃客户端发现 `5 → 1` 不连续 → **全部请求全量快照 = 重启即全量风暴**。
- **建议方向**：明确重启语义：① 重启后所有连接强制全量快照（Gateway 通知、客户端丢弃旧 commitId 记忆），或 ② commitId 用"时间戳/实例 id + 递增"组合使其跨重启单调。需写死，不能留给实现猜测。
- **状态**：☑ 定案（2026-08-02，用户定案：重启后所有连接强制全量快照）
- **定案记录**：进程重启 = **全量基线重置**——commitId 归零重新计数；Gateway 检测 Service 实例标识变化（注册 Router 的实例 id）**主动通知**受影响连接"丢弃旧 commitId 记忆"，客户端丢弃旧 commitId、统一请求全量快照重建基线；全量为**受控一次性**（Gateway 统一触发、按连接有序下发），杜绝"各客户端各自发现 `5→1` 不连续、各自盲目全量"的随机风暴；重启全量与重连全量同路径（5.1），客户端无需区分触发原因。**否决方案②**：投影不持久化、内存提交序列重启即丢，增量连续无从继续，时间戳/实例 id 组合无法避免全量，只会把受控通知退化成盲目探测。已回写 architecture.md 8.2 重启语义段、12.1 验证项、决策表 #46。

### R19. 事件通知 RPC 的重复送达

- **优先级**：P1
- **涉及章节**：8.2、9.3
- **问题**：事件通知 RPC 走可靠通道但底层是 at-least-once（9.3）——**重试会重复送达** → 客户端同一事件触发两次表现（两次飘字、两次动画）。文档只说"丢失仅损表现"，没提重复。
- **建议方向**：事件 RPC 带 eventId，客户端对最近 N 条去重（与服务端幂等表对称、成本极低）；或显式声明"重复表现可容忍"为已接受语义。
- **状态**：☑ 定案（2026-08-02，用户定案：事件 RPC 不带 eventId，一次发起就是一次通知）
- **定案记录**：事件通知 RPC = **服务器 → 客户端的一次性单向通知（fire-and-forget）**，**无 eventId、无应用层重试、无去重**——服务端一次发起即一次送达语义，**重复不存在**：at-least-once 重试只属于请求-响应式 `Call`（9.3，服务端等待结果、超时才重试），事件通知发出即弃、不等待不确认，应用层重试前提不存在，重复的前提也就不存在。**但传输层丢包重传保留（用户补充修正）**：事件通知与投影走同一可靠通道（TCP/KCP 自带有序与重传）——普通丢包由传输层自动重传解决、不丢事件；**只有不可抗力才真正丢包**（连接断开、进程崩溃、出站背压主动丢弃 8.2），此时代价已闭环：仅损表现、投影全量兜底、不重放。已回写 architecture.md 8.2 事件通知段补"一次性通知无 eventId + 传输层重传保留"语义、12.1 验证项、决策表 #47。

### R20. 批次层文档的归属与多实例广播

- **优先级**：P1
- **涉及章节**：9.5、8.4、11
- **问题**：`RewardBatchInfo` 是 `[Persistent] BehaviorInfo`，但**它属于哪个 Actor？** 复合键是 `actorId + behaviorInfoType`——批次的 actorId 是什么？多实例 player.service 下每个实例各持一份内存批次表、TimerWheel 每实例都跑——**开放广播每个实例都发**，玩家收到多次；过期移除各实例独立，时序可能不一致。
- **建议方向**：批次归一个固定域 actorId（或走全局文档集合而非 BehaviorInfo）；广播明确**只从唯一 holder 发出**（或接受重复广播 + 客户端/领取幂等去重，显式声明）。
- **状态**：☑ 定案（2026-08-02，用户定案：批次领取是"在线时做一次"的事情，检测时机在玩家激活；行为生命周期定四件套）
- **定案记录**：R20 不是广播一致性问题，而是**检测时机问题**——批次领取是**玩家激活时做一次**的惰性检测，非持续一致性需求。①**生命周期四件套定案**：`OnLoad` 加载（BehaviorInfo 进内存）、`OnUnload` 卸载（冷卸载前，dirty 先写回）、`OnEnter` 进入活跃、`OnLeave` 离开活跃——**数据维度（Load/Unload）与活跃维度（Enter/Leave）正交**："活跃"= 有可推送投影目标（player：session 建立/缓冲期结束；club：有在线成员/最后成员离线），不是 player 专属"上线下线"，club 等无 session 类型同样适用；够用、不引入 OnTick 扫描；②**领取检测时机**：挂 `OnEnter`（进入活跃时）/`OnLoad`（离线被 `SeekDeep` 拉起时，登录 Job 求差集），复用 9.5 既有"上线/被激活时求差集"语义并确认为唯一检测时机；③多实例各广播/各移除退化为**通知噪音**：开放广播重复仅损表现（R19 通知语义），过期移除以玩家激活时刻所在实例内存批次表为准——一次性快照判定，批次过期作废天然容忍实例间时序偏差；④**归属**：批次为 Service 级共享缓存（各实例自载内存副本、Mongo 权威），不参与 Actor 私有归属模型——检测只在激活时刻发生，副本偏差在一次性快照判定下可容忍，无需唯一 holder。已回写 architecture.md 4.1 状态定义、6.1 生命周期四件套、9.5 领取检测时机段、12.1 验证项、决策表 #48。

### R21. 单线程共享下 CPU 密集 Job 阻塞全进程（无硬性运行时上限）

- **优先级**：P2
- **涉及章节**：3.1、3.3、12.1
- **问题**：单线程是**全进程共享**的。一个无 yield 的 CPU 密集 Job（Analyzer 漏网、误用库、正则爆炸）会**阻塞所有玩家**。看门狗 500ms 只能 dump 报警，**无法恢复**；"长同步任务走专用 Service"是规范约束，不是运行时保障。
- **建议方向**：把这一点显式列为**已知边界**（Analyzer + 专用 Service + 告警三道软防线）；可选加固：每轮给 Job 的 MoveNext 段设墙钟预算，超预算记慢 Job 并强制结束（结束语义 = 取消 + 回滚，可预测）。
- **状态**：☑ 定案（2026-08-02，用户确认：超时检测只覆盖挂起等待段，CPU 密集卡死不超时，进程内中断回滚不可行，兜底在进程级）
- **定案记录**：**超时检测分两层**——①**等待段超时保证**（R10/决策 #34）：每个等待器（WaitForLoad/WaitForRpc）强制 deadline，超时 = 唤醒 + Job 失败回滚——Job yield 后调度器有控制权、检查有机会执行，此层可保证；②**无 yield 的 CPU 密集段不会超时**：检查只在 yield 点/等待器触发，卡死段调度器无控制权、检查根本没机会跑，看门狗只能 dump。**进程内强制中断 + 回滚不可实现**：协程协作式、无 yield 点即无抢占注入点；即使强杀线程，回滚逻辑（finally/调度器 Rollback/`_bak_` 快照恢复）在 Job 栈上执行不到，内存半更新状态比卡死更糟——单线程模型没有第二个执行上下文能跑回滚。**真正的"中断回滚"在进程级**：不可控/CPU 密集工作下沉专用 Service 进程，外部看门狗（Controller）按心跳超时杀进程重启，回滚 = 崩溃窗口语义（8.4：内存 dirty 丢弃、Mongo 真相恢复、<200ms 丢失可接受），故障半径圈死、不伤主 player.service；若为确定性 bug 则重启复发，专用进程只圈半径、根因仍靠 Analyzer + 代码规范。**否决"墙钟预算 + 强制结束"作为进程内保障**：预算只能在 yield 点检查（对单段卡死无效），强制结束 + 回滚进程内不可实现。已回写 architecture.md 3.3 卡死防护段补边界、12.1 验证项、决策表 #49。
- **追加定案（2026-08-02，用户采纳"墙钟预算"方案）**：**墙钟预算层落地为"慢 Job 检测 + yield 点取消回滚"**——调度器为每轮 `MoveNext` 段打点计时（段返回后结算，阈值可配），超预算 → 记慢 Job + 告警 + 标记该 Job，在**下一个 yield 点协作式取消 + 回滚**（R10 取消链 + `_bak_` 快照回滚，结束语义 = 取消 + 回滚，可预测）。**抓取范围边界**：预算检查只在段返回后 / yield 点执行——能抓"慢但会返回"的段，**抓不住"永不返回"的无 yield 卡死段**（段未返回则检查点执行不到），后者仍由看门狗 dump + 专用 Service 进程级杀重启兜底（原定案不变）。**补充 `WaitForTask<T>` 任务级隔离路径**：可拆纯计算段抛线程池 + deadline 回滚（子任务不碰共享状态、卡死仅泄漏有界线程不阻塞主线程），是进程内的软加固，不改变"卡死兜底在进程级"的定案。已回写 architecture.md 3.3（墙钟预算边界段 + 三层防护第 2 层）、12.1 验证项、决策表 #49。

### R22. 在线玩家漏收发放广播的兜底

- **优先级**：P2
- **涉及章节**：9.5、10.2
- **问题**：在线玩家兑奖依赖"收到广播"——广播是尽力投递（10.2），**漏广播的在线玩家永远不会知道自己能领**。文档只给了离线/上线时的差集兜底，**没给在线漏收者的时机**。
- **建议方向**：把"求差集兑奖"并入在线玩家的既有 Actor 级周期任务（每日刷新 Job 顺手求一次差集），在线漏广播者最迟次日自愈。
- **状态**：☑ 定案（2026-08-02）
- **定案记录**：**在线漏广播者自愈 = 提醒层 + 正确性层双保险**。**提醒层（可丢，10.2）**：模板/批次发布时实时广播在线玩家"有可领"——Service 向各 Gateway 群发一条轻量通知，粒度 O(Gateway 数) 而非玩家数（复制在 Gateway 连接层、本职能力），只发"未读数+1"小包、内容打开时渲染，代价可忽略；广播尽力投递、可丢。**正确性层（服务端，永不丢）**：①判定/入账永远在服务端 Job（校验时间窗 + 未领）；②离线/上线靠登录 Job 差集（9.5 既有）；③**在线漏收者 = 既有 Actor 级周期任务（每日刷新 Job）顺手求差集，最迟次日自愈**——防"通知丢失 + 客户端永不重启"的边角，从原案的"唯一手段"降为"通知/感知失效时的保险丝"。**就绪形态区分（一并定案）**：领取机制同一套（批次/模板 + 差集），就绪时刻分**广播型**（未知事件，运营/系统随时触发，靠通知提醒，可丢）与**计时型**（已知时间轴，如"N 分钟后可领"：服务端下发 `readyAt` 绝对时间戳，客户端展示倒计时，点击时服务端惰性校验 `now ≥ readyAt`；服务端**不跑 per-player 定时器**——到点触发仅对在线有意义且数量随玩家数爆炸，是反模式；"到点自动入账"也做惰性：下次激活/周期补 `readyAt ≤ now` 未领者）。已回写 architecture.md 9.5（R20 段补在线兜底 + 就绪形态/提醒来源段）、11 章 Actor 级周期职责、12.1 验证项、决策表 #48。

## 实现期架构裁决（2026-08-03，用户当场定案，非 R 系列评审条目）

> 来源：Phase 1 实现中用户对"主工程为何有业务命名"的连环质询，四连裁决收窄了 Actor 形态。已回写 `architecture.md`：1.2/2/3.1/4.1/6.1/7.1/12.1/13/决策表 #50。

### 裁决①：主工程不得出现业务命名
- 质询：「当前的 Queen 为什么会有业务的东西？不应该是一个 Service 的基础件么？」
- 结论：主工程回归**纯运行时基础件**；Wallet/Bag/Player 等业务桩移入 `Queen.Tests` 作为测试基准（2026-08-03 推进完成）。

### 裁决②：新架构没有 Actor class，应该是 ECS 式结构
- 质询：「你是不是借鉴了旧工程？实际上我们的新架构，没有 Actor 的。应该是类似于 ECS 那种结构」
- 核实（2026-08-03）：Comp 组件树沿袭旧工程（唯一实锤借鉴点，e96c484^ 与新版逐字一致）；Behavior 名来自旧工程 RoleBehavior，但四钩子 + Info 分离是 v4.1 重构；BehaviorInfo 旧工程零命中、纯新设计；Actor 是 v4.1 文档第 4 章 Virtual Actor 正式概念，计划 Task 1.3 也明确建 Actor.cs；文档 0 处 ECS。当前 Actor.cs 结构上 ≈ ECS Entity（纯身份 + 生命周期），Behavior≈逻辑、BehaviorInfo≈数据——结构趋同 ECS，但命名与职责按下述裁决④进一步收窄。

### 裁决③：Actor 只是 ID，把 BehaviorInfo 串起来；Behavior 与 BehaviorInfo 不强绑定
- `Behavior<T> where T : BehaviorInfo` 泛型基类**作废**；Behavior 纯逻辑（`actorId` + `engine` 注入 + 四钩子），Job 内取数据一律 `JobContext.Get/Load<T>()`。
- 数据全部挂在 Actor 的 DataStore 上（显式 `AddInfo<T>()` 挂载）——**Actor 虚拟化（离线激活/迁移）以此为前提**。

### 裁决④：Actor 就不应该有一个 class 存在（拍板"现在就按 Service 容器设计"）
- **`Actor.cs` 删除**，身份降为纯 `ulong` ID；"串起机制" = **Service 容器的 ID→DataStore 注册表**。
- `Service : Comp`（每进程一个）：`stores`（ID→DataStore）+ `behaviors`（ID→Behavior 列表）+ 在线集。API：`AddActor(id)→DataStore`（重复抛异常）/`GetStore(id)`/`RemoveActor(id)`（在线先 Leave→逐行为 Unload→销毁 store）/`AddBehavior<T>(id)`（注入 engine+actorId，按 loaded/online 补触发）/`AddInfo<T>(id)`/`Load/Enter/Leave/Unload(id)`。
- 调度链：`JobScheduler.Post` 经 `engine.service.GetStore(actorId)` 直连 `job.data`；`JobContext` 静态路由 `current!.data`；`Job.ReleaseRefs` 走 `data.Release(type)`。
- 数据访问范式：Job 内 `JobContext.Get/Load<T>()`；Job 外 `engine.service.AddActor(id)` + `store.AddInfo<T>()`；生命周期 `service.Load/Enter/Leave/Unload/RemoveActor(id)`。
- 验证：`dotnet build` 0 错误 0 警告，`dotnet test` **59/59 全绿**。
- SG 生成器（BehaviorInfoGenerator）零依赖 Actor/Behavior，免改。
